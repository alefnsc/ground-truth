# Demo Implementation Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** A single-page web app that shows the two currencies (energy and load) for a day of exercise under Earth, Moon, Mars and ISS gravity, and measures a real set from a phone camera or a video file.

**Architecture:** A third workspace package, `packages/demo`, built with Vite and plain TypeScript (no UI framework). All numbers come from `@ground-truth/physics` and `@ground-truth/capture`. The demo adds three things: a small pure **scenario model** (preset sessions → energy, load, stimulus, deficit), a thin **pose adapter** (pose-model landmarks → `PoseFrame`), and DOM views that only render what the pure code returns. Everything runs in the browser; nothing is sent anywhere.

**Tech stack:** TypeScript (strict), Vite, Vitest, `@mediapipe/tasks-vision` (Pose Landmarker, Apache-2.0) as the only new runtime dependency.

**Authority:** [`docs/strategy.md`](../strategy.md) §2, §3, §7, §10, and the two package READMEs.

## Global constraints

- **Local only.** No network calls except loading the pose model and its WASM files. No analytics, no storage of video, no upload. Video frames never leave the page.
- **Every number shows where it came from.** Each displayed value carries a provenance chip: `MEASURED` (camera), `MANUAL` (entered), `MODEL` (a published formula with stated parameters), `ASSUMPTION` (a parameter this demo chose), `CALIBRATED`, or `ESTIMATE`. The scenario model returns the provenance with the number; views never invent one.
- **No number without a source.** If the model cannot compute something honestly, the view shows a dash and the reason, not a guess.
- **Wording.** "Load accounting", never bone loss or bone density. No kilocalories as a single figure. No clinical language. No claim of accuracy on real video. Camera results repeat the capture package's caveats in the UI: confidence is capped, scale is the largest error.
- **No brand.** No company name or logo anywhere. The title is "Ground Truth".
- Pure logic lives in `src/model/` and `src/pose/` and is unit-tested. Files under `src/view/` contain DOM code only and no arithmetic beyond formatting.
- Works at phone width (360 px) and on a laptop. Keyboard-operable controls, visible focus, text contrast at least 4.5:1, respects `prefers-reduced-motion`.
- No UI framework, no CSS framework, no chart library. Hand-written CSS with custom properties; any chart is inline SVG generated from data.
- Commit after each task. `npm test` and `npm run typecheck --workspaces` clean; `npm run build -w @ground-truth/demo` succeeds.

## What the brief's demo script says, and what this plan does about it

Brief §10 scripts five beats. Two of them assert outcomes ("Switch to ISS. Energy barely moves. Load collapses"). The demo must show what the model actually computes, not what the script hopes. If a scripted beat does not come out of the physics, the README records the real numbers and says so. The cycle-ergometer beat (large energy, no load term) and the provenance beat are structural and will hold.

Per-compartment divergence (trabecular vs cortical) is **not modelled** by the physics package and is not shown. The deficit view says so.

### Task 2: Scenario model

**Files:** `packages/demo/src/model/scenarios.ts`, `packages/demo/src/model/day.ts`, tests `packages/demo/test/scenarios.test.ts`, `packages/demo/test/day.test.ts`.

**Types**

```ts
export type Tag = "MEASURED" | "MANUAL" | "MODEL" | "ASSUMPTION" | "CALIBRATED" | "ESTIMATE";
export interface Quantity { value: number | null; unit: string; tag: Tag; note: string } // null => not computable; note says why
export interface SessionResult {
  id: string; title: string;
  energy: Quantity;        // mechanical work, J
  peakLoad: Quantity;      // N
  bout: LoadBout | null;   // null when the session has no skeletal load term in this model
  details: Quantity[];     // parameters and intermediate values shown on expand
}
export interface Person { massKg: number; legLengthM: number }
export interface Env { body: Body; gEnvMs2: number }
```

**Presets** (each a pure function `(person, env, params) → SessionResult`; every parameter is exported with a comment giving its tag and source)

1. **Treadmill run** — params: `durationS = 1800`, `cadenceStepsPerMin = 170` (ASSUMPTION), `comVerticalM = 0.08` (ASSUMPTION), `earthPeakMultiplier = 2.5` (ASSUMPTION: running peak vertical ground reaction force is commonly cited at 2–3 body weights), `supportFraction = 0.7` (brief §2, used on the ISS only).
   - `F_eff = treadmillEffectiveForceN(m, g_env, body === "ISS" ? supportFraction : 0)`.
   - Energy `= steps × F_eff × comVerticalM` (brief §2 `W_per_step ≈ F_eff · Δz_COM`), tag MODEL.
   - Peak load: on the ISS, `earthPeak × (1 − GENC_2010_PEAK_LOAD_DECREMENT.running)` where `earthPeak = earthPeakMultiplier × m × 9.81`, tag MODEL (measured decrement); elsewhere `earthPeakMultiplier × F_eff`, tag ASSUMPTION (peak scales with effective weight). In TRANSIT with no harness the session is not possible: `value: null` with the reason.
   - Detail: `froudeTransitionSpeedMs(g_env or harness gravity on the ISS, legLengthM)`.
2. **Resistive squats** — params: `deviceForceN = 1000` (MANUAL), `sets = 3`, `repsPerSet = 12`, `strokeM = 0.5` (MANUAL), `replaceBodyWeight = false`.
   - With `replaceBodyWeight`, the device force becomes `deviceForceForEarthEquivalenceN(1000 + m·9.81, m, g_env)`.
   - Peak load `= totalForceN(device, m, g_env)`, tag MODEL (static; the inertial term is not included).
   - Energy `= reps × totalForceN(...) × strokeM`, concentric only, tag MODEL.
3. **Cycle ergometer** — params: `durationS = 2700`, `displayedPowerW = 150` (MANUAL).
   - Energy `= ergometerWorkJ(...)`, tag MODEL (CEVIS correction). Detail: `metabolicRange` of it, tag ESTIMATE.
   - Peak load: `value: null`, note "no skeletal load term in this model"; `bout: null`. Identical in every environment.
4. **Camera set** — built from a capture result (Task 5): energy = total positive work (MEASURED), peak load = max peak force (MEASURED), bout = `{ cycles: reps, peakLoad: maxPeakForce }`.

**Day** (`day.ts`)

```ts
export interface DayResult {
  sessions: SessionResult[];
  totalEnergy: Quantity;          // sum of non-null energies
  stimulus: Quantity;             // dailyLoadStimulus of all bouts
  earthStimulus: Quantity;        // same person, same sessions, body EARTH
  stimulusRatio: Quantity;        // stimulus / earthStimulus
  cyclesToMatch: Quantity;        // cyclesToMatch(peak ratio of the dominant bout), null when ratio is 0 or ≥ 1
}
export function computeDay(person, env, sessionSpecs): DayResult;
export function deficitOverMission(day: DayResult, days: number): Quantity; // (earthStimulus − stimulus) × days
```

**Tests** (person 78.4 kg, leg 0.9 m)

Derive every expected value by hand in a comment from the physics formulas; do not paste numbers from running the code. Cover at least:

| Case | What to assert |
|---|---|
| Cycle, any two environments | same energy (365 040 J for the defaults), `peakLoad.value === null`, `bout === null` |
| Squats, Earth vs ISS, defaults | Earth peak `1000 + 78.4×9.81`; ISS peak `1000`; energy scales the same way |
| Squats, ISS, `replaceBodyWeight` | peak equals the Earth peak |
| Treadmill, Earth | `F_eff = m·9.81`; energy `= 5100 × F_eff × 0.08`; peak `= 2.5 × F_eff` |
| Treadmill, ISS | `F_eff = 0.7·m·9.81`; peak `= 0.25 × 2.5 × m × 9.81`; tag MODEL |
| Treadmill, Moon | peak tag ASSUMPTION |
| Treadmill, TRANSIT | `energy.value === null` with a reason |
| Day on Earth | `stimulusRatio` = 1, `cyclesToMatch.value === null` |
| Day on the ISS | `stimulus < earthStimulus`; ratio matches a hand calculation; `cyclesToMatch` finite |
| A day of only cycling | `stimulus` = 0 and the ratio's note explains it |
| `deficitOverMission(day, 180)` | `(earth − achieved) × 180`; zero on Earth |
| Every `Quantity` returned | has a non-empty `note` and a tag from the union |

### Task 4: Pose adapter

**Files:** `packages/demo/src/pose/landmarks.ts`, `packages/demo/src/pose/source.ts`, test `packages/demo/test/landmarks.test.ts`.

`landmarks.ts` (pure, tested):

```ts
export const LANDMARK = { LEFT_EYE: 2, RIGHT_EYE: 5, LEFT_WRIST: 15, RIGHT_WRIST: 16, LEFT_ANKLE: 27, RIGHT_ANKLE: 28 } as const;
export type Side = "LEFT" | "RIGHT";
export interface Landmark { x: number; y: number; visibility?: number }

export function toPoseFrame(tS: number, landmarks: readonly Landmark[] | undefined, side: Side): PoseFrame;
// no detection or a missing landmark => { tS, wristY: 0, visibility: 0 }

export function pickSide(samples: readonly (readonly Landmark[])[]): Side;        // the wrist with higher mean visibility
export function calibrationFromLandmarks(landmarks: readonly Landmark[], side: Side): { eyeY: number; ankleY: number } | null; // null when either landmark's visibility < 0.5
```

Confirm the six landmark indices against the installed package's types or documentation and record where you confirmed them.

`source.ts` (DOM, not unit-tested): opens the camera (`getUserMedia`, rear camera preferred) or a chosen video file into a `<video>`; loads the Pose Landmarker (`FilesetResolver.forVisionTasks`, `PoseLandmarker.createFromOptions` with `runningMode: "VIDEO"`, `numPoses: 1`); and yields `{ tS, landmarks }` per video frame. **Timestamps must be capture time**: use `requestVideoFrameCallback` and its `mediaTime` (seconds) for files and camera where available, and never process the same `mediaTime` twice. The model and WASM URLs are two exported constants at the top of the file with a comment that an offline build must vendor both.

**Tests** (`landmarks.test.ts`): mapping of each side; missing detection → visibility 0; `pickSide` chooses the more visible wrist; calibration returns null on a hidden ankle; y is passed through unchanged (the capture package handles orientation).

### Task 5: Capture view

**Files:** `packages/demo/src/view/capture.ts`, `packages/demo/src/model/captureFlow.ts`, test `packages/demo/test/captureFlow.test.ts`.

`captureFlow.ts` (pure, tested): a small state machine `idle → calibrating → ready → recording → analysed | refused`, and the function that turns recorded frames plus inputs into either a camera `SessionResult` or a refusal with human-readable reasons (one sentence per `RefusalReason`).

The view, in order:
1. **Protocol card** (always visible): side-on to the camera; hold the weight still for a second before the first rep and before putting it down; start and stop recording while still.
2. **Source**: "Use camera" or "Open a video file". Live preview with the tracked wrist drawn as a dot.
3. **Scale**, two methods:
   - *Known length (preferred)*: the user holds an object of known length vertically at the wrist, freezes the frame, taps its two ends, and types the length.
   - *Stature*: the user stands upright side-on, types their height; the eye and ankle landmarks are read from the frozen frame.
   The chosen method and the resulting metres-per-unit are shown, tagged ESTIMATE, with the sentence "scale is the largest error in this measurement".
4. **Load**: mass of the weight (kg), environment (defaults to Earth), optional constant device force.
5. **Record / Stop**.
6. **Result**: either the refusal reasons, or per rep: positive work, peak force, range of motion, lift time, and — when present — a visible note for `filterLimited` ("too fast for the filter; work and peak force are under-read") and for `trimmedRangeFraction < 0.9` ("measured over N % of the detected movement"). Session totals, confidence with the sentence "grades the recording conditions, not accuracy; capped until validated on real video". A button **Add to today** puts the set into the Two-currencies view as a MEASURED session.

**Tests** (`captureFlow.test.ts`): state transitions; a synthetic session (reuse the capture package's test helper by importing it, or a small local generator with a seeded sequence) produces a `SessionResult` with MEASURED tags and a bout; a refused session produces sentences and no numbers; a rep with `trimmedRangeFraction` 0.5 carries the note.

**Check:** in the dev server, the view loads, the pose model loads, opening a video file runs frames through the adapter without errors in the console, and a refusal renders. Real-camera behaviour is a manual check on a phone and is NOT claimed by this task.

## Deviations recorded

What the build does differently from, or in addition to, this plan, and why. (Review of 2026-10-09; see the demo's README for the numbers.)

- **Provenance tags.** The plan prescribed `MODEL` for the treadmill energy and for the ISS treadmill peak load, and
  `MEASURED` for a camera set. A number is no more certain than its least certain input, so: treadmill energy and the
  ISS peak are `ASSUMPTION` (cadence, centre-of-mass rise and the 2.5 body-weight multiple are assumptions); the day's
  tags follow; a camera set is `ESTIMATE`, tied to the capture package's `VALIDATED_ON_REAL_VIDEO` constant. Derived
  quantities are built with one helper (`derive`) so a derived tag cannot be typed by hand.
- **Per-leg squat bout.** The plan did not say what a squat bout is. The run bout is the force through one leg; the
  squats' total force goes through both, so the bout takes half of it (one cycle per rep). Treadmill cycles are steps / 2
  per leg. Both are assumptions and listed as such.
- **Content-Security-Policy.** `index.html` sets `connect-src 'self' https://cdn.jsdelivr.net https://storage.googleapis.com`.
  The plan said "no network calls except loading the pose model and its WASM files"; the pose library also posts usage
  metrics to Google every 60 s, so the page blocks that request mechanically instead of relying on the sentence.
- **Refusal without capture timestamps.** In a browser without `requestVideoFrameCallback` the adapter would sample
  `currentTime` on animation frames; the plan allowed that fallback, but its timestamps carry scheduling jitter, so the
  view refuses to record there with a plain sentence.
- **The deficit is also shown as Earth-days of loading missing**, and cycles to match names the bout it refers to.
- **Additions beyond the plan, kept:** an "Include in today" checkbox on every session card; Remove on camera cards; two
  sliders as a keyboard alternative to tapping the two ends of a known length; playing a video file at half speed so
  that the pose model keeps up with every frame (frame times are the video's own either way); and a failed state with a
  sentence when a recording cannot be analysed.
